# ADR-0015: Per-component versioning and changelogs

- **Status:** Accepted
- **Date:** 2026-09-25

## Context

The owner requires that **every sub-piece** of DBR² (API, backend, frontend and so on) track its own version and changelog, using the scheme `MAJOR.MINOR.BUGFIX.BUILD` wherever possible.

## Decision

### Version format

`MAJOR.MINOR.BUGFIX.BUILD`: four non-negative integers with no leading zeros, for example `1.4.2.318`.

| Field | Increment when |
|---|---|
| **MAJOR** | The component's contract changes incompatibly (API, protocol, schema, CLI flags, configuration format) |
| **MINOR** | A backward-compatible feature is added |
| **BUGFIX** | A backward-compatible fix is made |
| **BUILD** | Set automatically by CI to the GitHub Actions `run_number` of the build workflow. It increases strictly and **never resets** when the other fields change. Local developer builds use `0`. |

- Each component's `VERSION` file holds `MAJOR.MINOR.BUGFIX` only. CI appends `.BUILD`.
- **Contract components** (the API contract, the agent protocol and the schemas) are not built artifacts, so their BUILD is always `0` (for example `1.2.0.0`).
- **Initial versions:** every component starts at `0.1.0` and stays below `1.0.0` until the v1.0 release. The v1.0 release sets every shipped component to `1.0.0`.

### Components

| Component | Path | What it covers |
|---|---|---|
| `api` | `api/` | The OpenAPI contract. `api/openapi.yaml` is generated by the server and committed so changes can be diffed. |
| `server` (backend) | `cmd/server/` | `dbr2-server`, including the Agent Gateway |
| `worker` | `cmd/worker/` | `dbr2-worker` and the Temporal workflows |
| `agent` | `cmd/agent/` | `dbr2-agent` |
| `reposerver` | `cmd/reposerver/` | `dbr2-reposerver` |
| `cli` | `cmd/dbr2/` | `dbr2` CLI |
| `web` (frontend) | `web/` | `dbr2-web` (Next.js console) |
| `agent-protocol` | `proto/agent/` | gRPC contract between the gateway and the agent |
| `manifest-schema` | `internal/manifest/` | Recovery manifest schema (ADR-0004); the manifest's `schema_version` carries this version |
| `db-schema` | `db/` | PostgreSQL migrations |
| `deployment` | `deployments/` | Compose files and packaging (RPM spec) |

Every component directory contains:

- `VERSION`
- `CHANGELOG.md`

**Shared code:** a change to shared code under `internal/` is recorded in the changelog of **each shipped component it affects**.

### Changelog format

Changelogs follow the Keep a Changelog layout, using the four-part version in each release heading:

```markdown
# Changelog — agent

## [Unreleased]
### Added
### Changed
### Fixed
### Removed
### Security
### Notes

## [0.2.0.57] - 2026-10-14
### Added
- Quiesce lease dead-man switch (ADR-0005).
### Notes
- Requires agent-protocol ≥ 0.2.0.0.
```

- Each entry is written in the same PR as the change, under `[Unreleased]`.
- On release, `[Unreleased]` becomes a versioned heading.

### Platform release

- A DBR² **platform release** has its own four-part version, for example `1.0.0.412`.
- The release includes a `release-manifest.json` that pins the exact version of every component.
- The root `CHANGELOG.md` summarizes each platform release and links to the component changelogs.
- `docs/roadmap.md` remains the project and work history, including decisions. The component changelogs are the user-facing record of changes.

### Where the four-part format can't be used

| Target | Representation |
|---|---|
| Go binaries | Full version injected at build time (`-ldflags -X`); printed by `--version` |
| Git tags | `<component>/v1.2.3.45` (for example `agent/v1.2.3.45`); platform releases use `v1.2.3.45` |
| OpenAPI `info.version` | Full `api` version (four-part) |
| npm `package.json` (web) | Semantic versioning requires three parts: `1.2.3`. The full `1.2.3.45` is exposed at runtime (environment variable and UI footer). |
| RPM | `Version: 1.2.3`, `Release: 45%{?dist}` (displayed as `1.2.3-45`) |
| DEB (v2) | `1.2.3.45` (valid as-is) |
| Container images | Tags `1.2.3.45`, `1.2.3` and `1.2` |
| Temporal worker build ID | Full worker version |

### Runtime visibility and compatibility

- Every binary supports `--version`.
- `GET /api/v1/version` returns the platform version plus the version of every component.
- The web console shows versions in its footer and on the About page.
- **Agents** report their `agent` and `agent-protocol` versions when they connect. The gateway rejects an agent whose agent-protocol MAJOR does not match, and flags one that is outdated.
- **Manifest readers** accept every earlier manifest-schema MAJOR (ADR-0003).
- **Database migrations** are forward-only. `db-schema` MAJOR changes require a documented upgrade path.

### CI enforcement (GitHub Actions)

- **Changelog check (PR):** if files under a component's path change, that component's `CHANGELOG.md` `[Unreleased]` section must gain an entry. The `no-changelog` label is allowed only for PRs that change nothing but tests, CI or docs.
- **API contract check (PR):** regenerate `api/openapi.yaml` and diff it against the committed copy. A breaking change requires an `api` MAJOR bump (for example using `oasdiff`).
- **Protocol check (PR):** `buf breaking` on `proto/agent/`. A breaking change requires an `agent-protocol` MAJOR bump.
- **Release workflow:** compute `VERSION` + `.run_number`, stamp the artifacts, move `[Unreleased]` to the release heading, tag the commit, and publish.

## Consequences

- Each PR carries a small extra cost (changelog lines), in exchange for a precise history per component.
- The documentation-driven roadmap change log and the component changelogs are both maintained. The roadmap update rule references this ADR.
