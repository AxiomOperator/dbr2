# Changelog — server

All notable changes to the `server` component. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions are `MAJOR.MINOR.BUGFIX.BUILD` (ADR-0015).

## [Unreleased]

### Added
- **Phase 7:** Protection Policies (cron or preset schedules with timezone, mode and Repository defaults, grandfather-father-son retention) with one Temporal schedule per application kept in sync; Recovery Contracts (max RPO, required components) evaluated every 5 minutes with violation/satisfaction alerts and a capture-time evaluation in each manifest; deletion with a 7-day grace period (recovery points and Repositories, typed confirmation and reason, undo); retention and deletion RPCs for the worker; skipped scheduled runs recorded.
- **Phase 8:** PostgreSQL/Redis detection (tooling images excluded), `database:<service>` components with online dumps, and the per-application database strategy (logical, volume, both); policies supply the consistency mode and Repository when an application sets none.
- **Phase 9:** verification RPCs and API (results: verified / verification_failed with details and alerts); escrow health (recipients, confirmation, recipient drift, 90-day re-confirmation, annual drill) checked hourly with `escrow.unhealthy` alerts; escrow package regeneration (password read from the reposerver, never stored); escrow drills.
- **Platform self-backup (Phase 9, ADR-0008, `internal/platform`):** Platform Recovery Bundle export — `tar` → `zstd` → age (binary) to every escrow recipient, encrypted inside dbr2-server: every `public` table as `COPY … (FORMAT binary)` from one REPEATABLE READ snapshot, `DBR2_SECRET_KEY`, the internal token, the Entra client secret (if set), each Repository's reposerver state (`GET /v1/state-export`; an unreachable reposerver is recorded as missing and makes the run Partial) and a `manifest.json` (versions, goose schema version, row counts, SHA-256 of every entry; Temporal excluded by design). `PlatformService` `BeginPlatformBackup`, `ExportPlatform` (server-streaming, 1 MiB chunks) and `RecordPlatformBackup` (audit `platform.backup.succeeded|partial|failed`, warning/critical alert on partial/failed); `repository.system.designated`; manual runs via `temporalx.StartPlatformOperation`.
- `dbr2-server admin restore-platform --bundle F --identity F [--secrets-dir D] [--reposerver-state-dir D] [--import-reposerver] [--database-url URL] [--force] [--verify-only] [--no-database]`: decrypts with an escrow identity (age X25519 or SSH key), verifies every digest, migrates a fresh database to the bundle's schema version, restores all tables in one transaction with `session_replication_role = replica` (TRUNCATE + `COPY FROM`, identity/serial sequences reset), applies newer migrations, writes the secrets as Compose secret files and the reposerver state archives (or imports them with `POST /v1/state-import`), then prints the next steps.
- **Notifications (Phase 7, `internal/notify`):** email (SMTP with STARTTLS, implicit TLS, or plain text for a localhost relay only; PLAIN auth; plain-text body with a console link) and webhook channels (HTTPS only except loopback; JSON payload; `X-DBR2-Event`, `X-DBR2-Delivery`, `X-DBR2-Timestamp` and, with a secret, `X-DBR2-Signature: sha256=<HMAC-SHA256(secret, timestamp.body)>`; 10 s timeout; redirects refused). A dispatcher in every dbr2-server instance fans outbox rows out to channels matching their event filter (exact or `prefix.*`) and minimum severity, then sends with retries (1 m, 5 m, 30 m, 2 h, 6 h; failed after 6 attempts); rows and deliveries are claimed with `FOR UPDATE SKIP LOCKED` (deliveries under a 5-minute lease), so several instances can run it. It runs every 10 s and shortly after any `alert.created` event. Outbox rows older than 24 h when first seen are marked without being sent. Webhook secrets and the SMTP password are sealed with `DBR2_SECRET_KEY`.
- `agent.offline` (warning; an active agent with no gateway session and no contact for 10 minutes, once per outage) and `agent.online` (info) alerts, raised through the outbox and audited as system events.
- **Live updates (Phase 6):** event bus (`internal/events`; Valkey pub/sub fan-out when configured) fed by the gateway (`job.progress` from agent command updates, `agent.status`, `inventory.updated`, agent alerts) and the protection service (`backup.updated`, `restore.updated`, `alert.created`); SSE endpoint with per-event permission filtering, 15 s heartbeats and per-message write deadlines.
- Application protection status and coverage (`protected`, `at_risk`, `failed`, `unprotected` with reasons; latest recovery point and attempt; running operation; per-component coverage against the latest manifest; unresolved dependencies); unified jobs list (backups and restores); fleet-wide containers and volumes views. Restore command progress needs `restore.read`. Agent command kinds are now recorded by their protocol name (e.g. `snapshot_components`) instead of `unknown`.
- **Restore (Phase 5, ADR-0017):** impact preview and collision detection from the manifest topology and the target inventory (container names, published ports, networks, volumes, bind paths, missing external networks; path remapping; in-place vs alternate host; images present or pulled); production-restore safeguards (`restore.production`, typed confirmation, mandatory reason); restore history (`restore_runs`); `PlatformService` `PrepareRestore` (re-validates before anything changes), `GrantRestoreAccess`/`RevokeRestoreAccess` (per-source READ grants on the reposerver), `UpdateRestore` (steps, outcome, audit and alerts).
- Backup plans now record the application topology (containers, ports, mounts, networks, volumes) in the manifest.
- **Repositories and key escrow (Phase 4, ADR-0008):** escrow recipients (age X25519 or SSH public keys; private keys rejected); Repository creation initializes Kopia on the reposerver with a generated password that is sealed into an age escrow package and **not stored**; Repositories stay `awaiting_escrow` until the package's confirmation code is entered; live reposerver status, certificate-fingerprint drift detection, per-host usage.
- **Backups (Phase 4):** manual backup start with a fast pre-check (host active, Repository ready); capture plan from the inventory (config with redacted metadata, Local volumes, bind mounts minus host plumbing, fsmeta per filesystem component, hooks resolved by service/container name, seed components, backup window for scheduled runs); application backup settings and host limits (audited before/after; host changes make the agent reconnect).
- Internal `PlatformService` on the control listener for dbr2-worker: `PrepareBackup` (idempotent per run), `EnsureAgentAccess` (creates `agent@<id>` on the reposerver and configures the agent over mTLS; the password is never stored), `CompleteBackup`, `GetRepository`, `ListRepositories`, `IndexRecoveryPoints` (the Repository wins; missing rows flagged), `RecordEvent`.
- Recovery-point index, alerts (notification outbox with acknowledgement), gateway handling of agent events (`quiesce.*` audit + alerts) and `Welcome.max_concurrent_jobs` from host settings.
- **Agent Gateway (Phase 2, ADR-0001/0016):** mTLS gRPC listener (`DBR2_GATEWAY_ADDR`, TLS 1.3); agent CA created on first start and stored sealed in PostgreSQL; enrollment with single-use registration tokens; `Connect` sessions with PostgreSQL leases, status, revocation and protocol-major checks, heartbeat round-trip latency; idempotent command dispatcher (re-sends on reconnect); certificate renewal with revocation of older certificates; `ForceReconnect`.
- Internal control listener (`DBR2_CONTROL_ADDR`, `DBR2_INTERNAL_TOKEN[_FILE]`) used by dbr2-worker to dispatch commands.
- **Inventory ingestion and analysis (Phase 3):** secrets sealed before storage; applications reconciled per host (Compose, standalone container, manual); missing applications flagged.
- Fleet service: registration tokens with join command, approve/suspend/resume/revoke with enforced transitions, on-demand discovery via Temporal, application metadata, manual grouping, Compose view and audited secret reveal.
- OpenTelemetry metrics `agent.connection_state` and `agent.latency`.

### Changed
- `golang.org/x/oauth2` 0.36.0 → 0.37.0 (Dependabot PR #3; used by Entra ID sign-in; applies to every Go binary).

### Added
- `DBR2_READY_HTTP_CHECKS` (`name=url,…`): non-critical readiness checks for other platform services. The dashboard's Platform status card now lists the Caddy edge proxy, dbr2-worker and dbr2-reposerver next to PostgreSQL, Temporal and Valkey (owner request).
- Component scaffold (Phase 1).
- `dbr2-server` subcommands: `serve` (default), `migrate [up|status]`, `openapi -o <file>`, `admin reset-master-password [--password-file] [--disable-totp]`, `healthcheck`, `version`.
- Master admin bootstrap on first start: random initial password written to a root-only file (`/var/lib/dbr2/master-admin-initial-password`, 0600), never logged.
- Authentication service: Argon2id passwords, progressive lockout (5 failures → 1 min … 1 h), per-IP login rate limit, replay-safe TOTP (AES-256-GCM-sealed seeds), server-side sessions (SHA-256 of token stored), idle timeout, personal API tokens, Entra ID OIDC with group-to-role sync (users without a role are denied).
- RBAC (six roles from final_stack plus `user.read`/`user.manage`), CSRF same-origin check for cookie-authenticated unsafe requests, client IP resolved only through trusted proxies.
- Append-only audit log with stable event IDs, mirrored to structured logs; notification outbox row for every master admin login.
- `slog` JSON logging with secret redaction and trace correlation; OpenTelemetry traces/metrics via OTLP (`DBR2_OTEL_ENABLED`).
- Readiness checks for PostgreSQL, Temporal and Valkey; hourly purge of expired sessions and OIDC state.

### Security
- Go toolchain pinned to go1.26.8 (`toolchain` directive in `go.mod`) so CI and release builds include the standard-library fixes for GO-2026-6218, GO-2026-6091, GO-2026-6090, GO-2026-6089, GO-2026-6088 and GO-2026-5972 (found by govulncheck when CI resolved `go 1.26` to go1.26.0). Applies to every Go binary.

### Notes
- The offline reset command is `dbr2-server admin reset-master-password` (run on the server host, e.g. `docker compose exec dbr2-server …`), not the `dbr2` CLI: it needs direct database access.
